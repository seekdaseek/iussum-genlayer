# Tooling feedback for GenLayer, from building MandateCourt

Engineer to engineer. Ordered by how much each item would have saved the next builder. Everything below was seen by me on 2026-11-12 or 2026-11-13 (dates given per item) unless the item says otherwise. Versions: `genlayer-js` 1.1.8 and 2.0.0-rc.3, `genlayer` CLI 0.39.2, `genlayer-test` 0.29.2, `genvm-linter` 0.11.0, studionet at `https://studio.genlayer.com/api` (chain id 61999), Bradbury RPCs as listed. Evidence for the numbers is in `results/` and `NOTES.md`.

## 1. A contract whose second line is a comment deploys "successfully" and does nothing (silent failure)
Seen 2026-11-12. Contract file: line 1 `# { "Depends": "py-genlayer:1jb45aa8..." }`, line 2 immediately another `#` comment, then code. The deploy transaction reaches `FINALIZED`, the receipt says `execution_result: ERROR`, `genvm_result.stderr` is empty, and the next `readContract` fails with `GenLayer RPC error (gen_call): Contract 0x... not found` / `ResourceNotFoundRpcError: Requested resource not found.` Adding a blank line after line 1 fixed it. I could not tell the cause from any output; I found it by bisection. A header parse error should say so in stderr, and `genvm-lint check` should flag a comment directly under the pin line (it reported `Lint passed` for the failing file).

## 2. Public Solana devnet RPC answers validators with HTTP 429 under batching and concurrency
Seen 2026-11-12 and 2026-11-13. A contract that sent one JSON-RPC batch with two `getTransaction` calls got `429` from validators for some cases on every attempt over 40 minutes (10 attempts, gaps 0 to 120 s, rotation 1 each time), while the same batch from a laptop returned 200 and the same transactions fetched as two single requests from the validators returned 200. After switching to one POST per transaction the cases passed. Later, three of my contract instances reading devnet at once got 25 `chain_unreachable` (HTTP 429, recorded in the contract) out of 101 runs; one instance at a time got 1 of 29. Advice for the docs: say that a validator-side RPC read should be one request per transaction, that public RPCs rate-limit validators as a group, and that a key stored in a contract is public, so a keyed RPC is not a fix. A recommended RPC proxy or a rate-limit-aware web helper would help most.

## 3. genlayer-js 1.1.8 `testnetBradbury` points at a consensus address with no code
Seen 2026-11-12. `genlayer-js@1.1.8` (npm `latest`): chain id 4221, `consensusMainContract` `0x0112Bf6e83497965A5fdD6Dad1E447a6E004271D`. `eth_getCode` for that address on `https://rpc-bradbury.genlayer.com` returns `"0x"`. Genesis hash on that RPC matches the docs (`0x17d89764d4f4f963158fc4c5e8f2cb670c2837740b35f37081c12860c3df97e4`), so the network is right and the preset is stale. A deploy from this preset cannot work. I did not deploy to Bradbury (no funds), so this is from reading chain state only.

## 4. genlayer-js 2.0.0-rc.3 Bradbury preset uses the chain RPC, which has no `gen_` methods
Seen 2026-11-12. The preset's consensus address `0x2E2766cbc3E5e61Ce93bBcdCBb3eAcB82082A019` has code, but its RPC is `https://rpc.testnet-chain.genlayer.com`, where `gen_syncing` and `gen_getContractSchema` answer `{"error":{"code":-32601,"message":"the method gen_syncing does not exist/is not available"}}` (the docs say this RPC has no `gen_*` methods). The same two methods on `https://rpc-bradbury.genlayer.com` exist (`gen_syncing` returns `syncedBlock/latestBlock/blocksBehind`). The working combination appears to be the RC address with the node RPC, which no released preset gives. A preset that works out of the box, or one clear sentence in the Networks page, would remove a day of guessing.

## 5. `canAppeal` and `getMinAppealBond` throw on studionet, so the appeal bond cannot be measured
Seen 2026-11-12. `client.canAppeal({txId})` throws `canAppeal not supported on this chain (missing appealsContract)`; `client.getMinAppealBond({txId})` throws `Appeal bond calculation not supported on this chain (missing feeManagerContract/roundsStorageContract)`. `appealTransaction({txId, value: 0n})` works on studionet and the round record shows `appeal_bond: "0"`. So anyone building on studionet cannot learn what an appeal costs before Bradbury, and Bradbury needs funds that require a human step. Publishing a representative bond figure, or letting studionet report a nominal one, would let builders reason about economics.

## 6. Appeals re-check the leader's proposal; they do not ask for a new answer
Documented, and confirmed on studionet 2026-11-12 and 2026-11-13: a validator appeal draws a fresh committee (7 validators on top of the original 5, 12 votes in total in my runs), which re-judges the existing proposal. In 2 of 2 cases where the first round had produced a wrong verdict, the appeal confirmed it (`appeal_failed: 1`, same result). That is a coherent design but not what "appeal" suggests to a user. A line in the Appeals page, with the consequence for contracts whose leader output can be steered, would help. Builders may want a second independent evaluation path.

## 7. `gen_getTransactionReceipt` and `gen_getContractState` are missing on studionet
Seen 2026-11-12. `{"jsonrpc":"2.0","error":{"code":-32601,"message":"Method not found: gen_getTransactionReceipt"}}` and the same for `gen_getContractState`, while the docs list both for the node RPC. `gen_getTransactionStatus`, `eth_getTransactionByHash` and `gen_getContractSchema` work. An integration written against the docs fails on studionet and passes on a node; the docs could say which methods a studionet has.

## 8. Asimov is dead on the wire but still listed by the CLI and the skill
Seen 2026-11-12. `https://rpc-asimov.genlayer.com` returns Cloudflare `error code: 522` for every method. `genlayer network list` (CLI 0.39.2) still prints `testnet-asimov  Genlayer Asimov Testnet`, the genlayer-cli skill lists `testnet-asimov` and says the faucet works for it, and the documentation has no mention of Asimov (0 matches in the full-documentation text). Drop it from the CLI and the skill, or say it is retired.

## 9. Direct-mode tests need `sdk_version="v0.2.16"` because the default 404s
Seen 2026-11-12. With `genlayer-test` 0.29.2, `direct_deploy(...)` downloads the "latest" GenVM release, `v0.3.0-rc7`, and fails: `urllib.error.HTTPError: HTTP Error 404: Not Found` from `https://github.com/genlayerlabs/genvm/releases/download/v0.3.0-rc7/genvm-universal.tar.xz`. That release ships `genvm-runners-all.tar.xz` and platform tarballs, not `genvm-universal.tar.xz`. `v0.2.16` has the universal tarball, so `direct_deploy(path, ..., sdk_version="v0.2.16")` works (the pinned runner hash from the docs loaded under it). The loader should fall back to the newest release that has the asset it needs. Also: the loader refuses two contract classes in one test (`only one contract is allowed; first: ... second: ...`), so a test that wants two instances of one contract cannot be written; a note in the testing docs would save time.

## 10. Studio returns an HTML page where the SDK expects JSON, and the error looks like a code bug
Seen 2026-11-12, 2026-11-13. A request body over about 1 MiB gets `413 Request Entity Too Large` from the web server in front of the RPC; the SDK surfaces it as `An unknown RPC error occurred.` with details `Unexpected token '<', "<html>... is not valid JSON`. I measured the usable argument ceiling at between 520,000 and 700,000 bytes (the signed transaction is hex-encoded). The same `Unexpected token '<', "<!DOCTYPE "... is not valid JSON` error appeared on about 2 in 250 ordinary submissions and reads under load (rate limiting or a gateway page, I could not tell which); on reads it can lose a result. The SDK should say "HTTP 413" or "gateway returned HTML (status ...)" and the docs should state the size limit.

## 11. Receipts list two of five validators as `ERROR` with a quorum message
Seen 2026-11-12. For every transaction only three validators execute; the other two appear in `consensus_data.validators` with `execution_result: "ERROR"`, `error_code: "CONSENSUS_VALIDATOR_QUORUM_REACHED"`, stderr `Validator execution cancelled after quorum`, vote `idle`. That is correct behaviour, but a tool that counts `ERROR` rows will think 40% of validators fail. It also means the "jury of 5 different models" is three judging models per case in practice. Mark these as `skipped` or document it where Optimistic Democracy is described.

## 12. Which model judged is hard to read, and labels changed between days
Seen 2026-11-12 and 2026-11-13. Validators report `policy:prd-gpt-5-4`, `policy:prd-gemini`, `openai/gpt-5.4`, `google/gemini-3-flash-preview` for the same kind of seat; the next day the same seats read `prd-gpt-6.1-sol`, `gemini-3.5-flash-lite`. For anyone publishing per-model results the label set is not stable. A documented mapping from alias to model and version in the receipt would make per-model measurements reproducible.

## 13. `genvm-lint` flags a valid nested helper
Seen 2026-11-12. `genvm-lint check` fails with `gl.nondet.* call in 'MandateCourt._chain_facts.<locals>.one' not reachable from equivalence principle block` for a nested function that is only called from inside the leader function passed to `strict_eq`. Inlining the helper removed the error. Reachability through nested local calls should be followed.

## 14. Docs show SDK names the released SDK does not have
Seen 2026-11-12. The Appeals and Finality pages use `client.getAppealCharge`, `waitForDecision`, `waitForFinalization`, `isSuccessful`, which exist in `genlayer-js` 2.0.0-rc.x but not in 1.1.8 (npm `latest`). The v0.6 migration page says to install the RC explicitly, which helps, but the other pages do not repeat it. A version badge on each SDK snippet would do.

## 15. Faucet needs 0.01 ETH on Ethereum mainnet (not reproduced by me)
Reported to me by the person I work for on 2026-11-13; I have **not** tried the faucet myself (it is behind a Cloudflare Turnstile check, which I do not complete). If true, a testnet faucet that requires mainnet ETH is a barrier for solo builders; a verifiable-human alternative or a funded-by-request path would help. Treat this item as unverified.

## 16. Explorer pages are not readable from validators
Seen 2026-11-12. From validators, `https://explorer.solana.com/block/1?cluster=devnet` returned HTTP 429, `https://solscan.io/...` HTTP 403, and `gl.nondet.web.render(url, mode="html")` on the Solana explorer raised `contract_error: exit_code 1`. A Solana JSON-RPC `POST` with `strict_eq` on one stable field worked. A short "what a validator can read" table (JSON-RPC yes, explorer pages no) in the web-access docs would stop builders from trying.
