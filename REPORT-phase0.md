## 4. Answers

### 4.1 Maximum input size a call accepts (measured, studionet)

| Argument bytes | Result |
|---|---|
| 10,000 / 100,000 / 200,000 / 400,000 / 480,000 / 520,000 | accepted, `last_len` read back equal |
| 700,000 / 1,000,000 / 4,000,000 | rejected at submission |

The limit is the HTTP front end, not GenVM: a JSON-RPC body of 1,000 KiB returns 200, 1,100 KiB returns **413 Request Entity Too Large**. The signed transaction is hex-encoded, so the argument is roughly doubled; the usable ceiling is **between 520,000 and 700,000 bytes of argument**, about 0.5 MB.

LLM path: a 64,000-byte and a 448,000-byte statement both went through `classify` and were accepted with 3 agree (label `yes`). So a prompt of about 448 KB reached three models without error. Whether the models read all of it or it was truncated upstream is UNTESTED (test: put the deciding sentence at the end of a 400 KB input).

Bradbury limits are UNTESTED and may differ (the node changelog mentions fee and size limits on leader receipts).

### 4.2 Equivalence principle variants

Four exist (docs:5218-5540, skill:129-216):

1. `gl.eq_principle.strict_eq(fn)`: every validator must return identical bytes. For deterministic data; documented as unsuitable for LLM output.
2. `gl.vm.run_nondet_unsafe(leader_fn, validator_fn)`: custom pair. The validator returns True/False; it can re-run the task and compare chosen fields.
3. `gl.eq_principle.prompt_comparative(fn, principle)`: validator re-runs, then an LLM compares both outputs against a principle string.
4. `gl.eq_principle.prompt_non_comparative(input, task, criteria)`: validator does not re-run; an LLM judges the leader's output.

The fit for "agree on an enum, not on prose" is **variant 2 with partial field matching**: the leader returns `{verdict, liable_party, reason_code, reasoning}`, the validator re-runs and returns True only if the three enum fields are equal; `reasoning` is stored and not compared. The docs call this Pattern 1 and recommend it over the wrappers. This is what the probe ran (label compared, `why` not compared), 6 of 6 LLM transactions accepted (3 classify, 2 large-prompt, 1 appealed).

Two consequences for MandateCourt that the docs state: the stored value is the **leader's** output only, validators' own answers are not persisted (docs:5271); and a validator that only checks the leader's enum is in the allowed set "is not performing consensus" (docs:5248), so the validator must re-judge.

### 4.4 Cost

- Studionet, measured: **zero**. Balance was 0 before and after 1 deploy, 17 writes and 1 appeal. The skill documents studionet as gasless.
- Bradbury: UNTESTED (no funds). Documented model (docs:1528-1542, 1787-1795): the sender deposits a fee budget covering validator time units, rotations, storage, receipt bytes, messages and any pre-funded appeal rounds; unused budget is refunded at finalization. Call bytes and nondet output bytes are priced per byte (`gasPerCallByte`, `gasPerNondetByte` in the SDK fee spec). No GEN figures are given.
- Mainnet: **nothing is published**. The docs contain two mentions of mainnet, neither about price. Fee parameters are described as governance values to be read from the network.

### 4.5 Appeals

How: `client.appealTransaction({txId, value})` (JS), `appeal_transaction` (Python), `genlayer appeal <txHash>` (CLI), during the appeal window after Accepted. Anyone can appeal. Documented cost: a charge read from `getAppealCharge` = bond + funding for the next round; a winning appellant gets 2.5× the bond back, a losing one forfeits the bond to the majority validators (docs:877-902). Committee growth 5 → 7 fresh → 11.

Measured on studionet, tx `0x75f7f78c8b64acbf8572be781aa1d5d8a12d6f4235f5cb67b3e5ca3201d99bc9`: accepted at 14.8 s, appeal sent at 15.6 s with value 0, status went back to COMMITTING, 7 new validators voted (12 vote entries in total, 7 committed in round 1), result ACCEPTED again at 23.7 s with `appeal_failed: 1`, FINALIZED at 45.2 s. Bond recorded: 0. So on Studio an appeal is free and adds about 9 s. `canAppeal` and `getMinAppealBond` both throw "not supported on this chain" on studionet, so **the real bond size is UNTESTED** and needs Bradbury.

Limit worth knowing: a validator appeal re-checks the existing leader proposal with a fresh committee; it does not ask for a new answer unless the appeal succeeds (docs:860).

### 4.6 Can an external or EVM-side caller read the final verdict

- SDK: `client.readContract(...)` returned the stored state after every call. Works.
- Plain HTTP JSON-RPC, no SDK, no key (measured on studionet): `gen_getTransactionStatus` → `"FINALIZED"`; `eth_getTransactionByHash` → full record including votes and the leader's returned value; `gen_getContractSchema` → method list. `gen_getTransactionReceipt` and `gen_getContractState` return "method not found" on studionet (documented for the node RPC; UNTESTED on Bradbury).
- Ghost contract: documented as an EVM contract at the same address on GenLayer Chain that routes calls and holds balance (docs:157, 439). On studionet there is none: `eth_getCode` at the contract address returns `0x`, and the docs say Studio has no EVM layer (docs:2602). The docs describe the Ghost as a proxy, not a copy of state, so **an EVM contract reading the verdict directly from the Ghost is not documented**; the documented route is the contract emitting a message to an EVM contract on finalization (docs:1106, 2873-2879). UNTESTED on Bradbury.
- For phase 3 (a script writing the GenLayer tx id next to iussum's verdict_id) the JSON-RPC read is enough.
